# Decisions

This is an index of verified architectural decisions. It does not replace detailed, accepted ADRs.

| Decision | Status | Source |
| --- | --- | --- |
| Home Assistant Custom Integration with Config Entry-based setup | Implemented | `custom_components/adaptive_areas/__init__.py`, `config_flow.py` |
| Python runtime is source of truth; dashboard uses DTOs and WebSocket transport | Implemented | `dashboard.py`, `websocket.py`, `frontend/adaptive-areas-panel.js` |
| Environment entities expose qualitative public data while detailed recommendations remain internal | Accepted | ADR: [adrs/001-public-environment-presentation.md](adrs/001-public-environment-presentation.md) |
| Shared agent baseline is `AGENTS.md`; Claude imports it via `CLAUDE.md` | Accepted | `AGENTS.md`, `CLAUDE.md` |
| Dashboard specification is versioned in `docs/specifications/dashboard.md`; no normative dependency on `.agents/` | Accepted | [specifications/dashboard.md](specifications/dashboard.md) §16 (E1) |
| Dashboard data is shaped per user role on the server; non-administrators receive aggregated presence sources and no control entity IDs | Accepted, implemented (independent re-review pending) | [specifications/dashboard.md](specifications/dashboard.md) §3.1 (E2) |
| Decision Trace is administrator-only, read-only, exposed per Area through `adaptive_areas/get_decision_trace`, with an export allowlist | Accepted, implemented (independent re-review pending) | [specifications/dashboard.md](specifications/dashboard.md) §4 (E3) |
| Decision Trace reason codes are recorded only in the trace; the public `last_reason` attribute stays unchanged | Accepted, implemented (independent re-review pending) | [specifications/dashboard.md](specifications/dashboard.md) §5 (E5) |
| Dashboard translations use Home Assistant's `frontend/get_translations` if the minimum version check passes; otherwise a new alternative is proposed | **Superseded (2026-11-22)** by the dashboard texts decision below | [specifications/dashboard.md](specifications/dashboard.md) §8 (E7) |
| Dashboard subscription follows the set of loaded Areas: `__init__.py` sends the internal dispatcher signal `SIGNAL_AREAS_CHANGED` after an entry is set up or unloaded; `subscribe_updates` rebuilds its entity index (one entity may map to several Areas, for example a child and its Meta Areas) and pushes the data-free event `{"areas_changed": true}`; the role is read for every pushed event. Additive: no storage, schema or entity change; existing area-summary events are unchanged | Accepted (independent re-review, 2026-11-20), implemented | `__init__.py`, `const.py`, `websocket.py`; tests `tests/test_dashboard_subscription.py`; [ARCHITECTURE.md](ARCHITECTURE.md) |
| Overview DTO is extended additively with floor metadata from the Home Assistant floor registry (`floor_id`, `floor_name`) and, for Meta-Areas, the IDs of their loaded physical members (`members`); missing values stay `null` or are omitted, never invented | Accepted (step 4.3, 2026-11-20), implemented | `dashboard.py` (`build_area_summary`, `_floor_name`, `_meta_members`); tests `tests/test_dashboard_permissions.py`; [specifications/dashboard.md](specifications/dashboard.md) §6 |
| **Superseded (2026-11-22):** Dashboard texts under the top-level category `dashboard` in `translations/en.json` and `de.json`, loaded via `frontend/get_translations`. Hassfest rejects this category (`[TRANSLATIONS] not a valid option at 'dashboard'`). Original decision: Home Assistant's `frontend/get_translations` is the target source (E7, option A); English as the fallback. Verified in the Home Assistant 2026.8.0 wheel (command, `async_get_translations`, English fallback merge, flattened keys `component.<domain>.<category>.<key>`). Migration and asynchronous loading are not yet implemented | Accepted and implemented (2026-11-21): ~400 texts and the trace labels live only in `translations/en.json` and `de.json` (category `dashboard`); the panel loads them via `frontend/get_translations`. Harness-tested (E7a–E7d, V10); not verified in a running Home Assistant instance | `translations/en.json`, `translations/de.json`, `frontend/adaptive-areas-panel.js` (`_loadTexts`), `tests/test_frontend_translations.py`, `tests/frontend/run.mjs`; [specifications/dashboard.md](specifications/dashboard.md) §8 |
| Dashboard presence distinguishes occupied, clear and unknown through the additive value `presence.state = "unknown"`; `occupied` stays a Boolean and reflects the automation decision. A Physical Area is clear only with at least one available presence source; a Meta-Area is clear only when every loaded member is clear. Automation logic is unchanged | Accepted (V06-P1, 2026-11-20), implemented | `dashboard.py` (`_presence_state`); tests `tests/test_dashboard_presence_state.py`; [specifications/dashboard.md](specifications/dashboard.md) §6 |
| Presence domains (`presence_device_platforms`): the Area editor offers exactly `binary_sensor`, `device_tracker`, `media_player` and `remote`. Stored values outside these four are kept, flagged and ignored by presence evaluation; no automatic deletion or data migration. The backend rejects a domain only when a save newly adds it; explicit removal is allowed. No new configuration key | **DECIDED / CLOSED** (product decision, final; not an open question) | `const.py` (`ALL_PRESENCE_DEVICE_PLATFORMS`), `area_config.py` (`_new_unsupported_presence_platforms`), `helpers/sources.py`; tests `tests/test_presence_domain_selection.py`, BR5–BR8 in `tests/frontend/run.mjs`; [specifications/dashboard-migration-matrix.md](specifications/dashboard-migration-matrix.md) "Entity filter rules" |
| An empty presence domain selection is allowed. No mandatory selection, no blocking validation, no automatic addition of default domains. The editor shows a factual hint only when the saved Area has no effective presence source (overview `presence.total == 0`); this count includes Presence Hold, BLE and Wasp in a Box sources when their features are enabled | **DECIDED / CLOSED** (product decision, final; not an open question) | `dashboard.py` (`presence.total`), `base/adaptive.py` (`get_presence_sensors`), `frontend/adaptive-areas-panel.js` (`_noPresenceSourcesHint`); tests BR12a/b, BR13 in `tests/frontend/run.mjs`; [specifications/dashboard-migration-matrix.md](specifications/dashboard-migration-matrix.md) "Entity filter rules" |

| Dashboard texts live in `custom_components/adaptive_areas/dashboard_texts/{en,de}.json`, outside `translations/`, because Home Assistant's translation schema (hassfest) accepts no custom top-level category. The panel loads them through the read-only command `adaptive_areas/get_dashboard_texts(language)`, available to every signed-in user. The response keeps the flattened keys `component.adaptive_areas.dashboard.<path>`; English is the fallback for every missing key or unsupported language; a load failure returns the error `dashboard_texts_unavailable`. The integration translation files keep only Home Assistant's categories | **DECIDED / CLOSED** (technical decision, final) | `dashboard_texts.py`, `websocket.py` (`websocket_get_dashboard_texts`), `frontend/adaptive-areas-panel.js` (`_loadTexts`); tests `tests/test_dashboard_texts.py`, `tests/test_frontend_translations.py`, E7a–E7d in `tests/frontend/run.mjs`; [specifications/dashboard.md](specifications/dashboard.md) §8 |
